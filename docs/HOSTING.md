# Hosting Kittok

An instance is a complete installation on a domain you control. Its users, sessions, invites, videos, and social data belong to its own PostgreSQL database. Media and client assets belong to its own storage volumes. You can use any domain or instance name.

## Docker Compose

1. Download and extract the Kittok source archive.
2. Run `npm run setup`, or the Docker-based Node setup command in the README. This creates `.env` with a random database password and preserves existing configuration on reruns.
3. Set `PUBLIC_ORIGIN` to your exact HTTPS origin, without a path; for example `https://cats.example.org`. Set `INSTANCE_NAME` and `INSTANCE_DESCRIPTION`.
4. Run `docker compose up -d --build`.
5. Run `docker compose exec app node scripts/create-user.mjs owner --admin`. Enter a new local password at the prompt. Password input is hidden. The command creates an administrator for this instance.
6. Configure DNS and an HTTPS reverse proxy. The app is published on `127.0.0.1:3210`. The database is internal to Compose. Copy `deploy/Caddyfile.example` into your Caddy configuration, replacing its domain.
7. Visit `/login`, choose the username/password option, and log in with your local account. Upload videos at `/account` afterward. The original feed reads the resulting PostgreSQL records and local media.

The database must become healthy before the app starts. The app downloads a signed-out client on its first startup. Later starts reuse the client volume. Allow several minutes for image building and the first download. `docker compose logs --tail=100 app` shows startup errors; `/health/ready` checks database connectivity.

Public instances require HTTPS. Cookies get `Secure`, `HttpOnly`, and `SameSite=Lax` attributes. `PUBLIC_ORIGIN` is authoritative; proxy headers cannot override it. Preserve the original `Host` header in your proxy. Match the proxy's upload limit and timeout to `MAX_VIDEO_MB` and the time needed to transcode uploads. Caddy's example starts at 100 MB. This release uses per-process rate limits keyed by the directly connected address; users behind a reverse proxy share that address's unauthenticated login limits.

The admin panel records each sign-up and login with its country, language, and device, and keeps sessions' devices and last activity. Set `IP_HEADER=x-forwarded-for` behind Caddy (or `cf-connecting-ip` behind Cloudflare) so the visitor's address is recorded instead of the proxy's; Kittok uses the last address in that header. Set `COUNTRY_HEADER=cf-ipcountry` behind Cloudflare to record countries; without it, countries show as Unknown. Only set these when your proxy overwrites the header, because visitors can send it themselves otherwise. IP addresses are never stored in plaintext. Each one is kept as a keyed hash, so admins can see accounts that share an IP and search by an IP they already know, but can't read it back. The hashing key lives in `MEDIA_DIR/private/ip-hash-key` (created on first start; set `IP_HASH_KEY` to supply your own) and must be kept with your backups, because new hashes won't match old ones without it. Everyone is asked once whether they mind the instance having their plaintext IP. For people who answer "I don't mind", the IP is also sealed to the instance's security key, and admins can show it on an account's Security tab by entering that key; shown IPs stay blurred until clicked, and every attempt goes to the audit log. Answering "I mind" (now or later, under IP address at `/account`) deletes anything sealed for that account. IP hashes and sealed IPs are cleared from the activity log after 90 days. Mention this collection in your instance's privacy policy.

Set up the security key once, on the server:

```sh
npm run ip-key
```

It prints a 128-character key once; save it somewhere safe, because it can't be recovered and the server keeps only its public half, so neither the database nor the server can read sealed IPs without it. Use `npm run ip-key -- --own` to type your own key (at least 64 characters, with letters, numbers and symbols), `-- --replace` to change it (asks for the current one and re-seals stored IPs), or `-- --reset` if it's lost (deletes every sealed IP). With Docker, run `docker compose exec app node scripts/ip-key.mjs`.

## Configuration

| Variable | Default | Purpose |
| --- | --- | --- |
| `INSTANCE_NAME` | `Kittok` | Instance display name |
| `INSTANCE_DESCRIPTION` | Short community description | About and instance API copy |
| `PUBLIC_ORIGIN` | `http://127.0.0.1:3210` | Exact public HTTPS origin, or loopback HTTP for development |
| `DATABASE_URL` | Required | PostgreSQL connection string for source installations; Compose supplies its internal URL |
| `POSTGRES_PASSWORD` | Generated by setup | Compose database password |
| `REGISTRATION_MODE` | `closed` | `closed`, `invite`, or `open` |
| `SMTP_URL` | Unset | Mail server for sign-up codes: `smtps://user:pass@host:465` (TLS) or `smtp://user:pass@host:587` (STARTTLS required unless the host is this machine). Any provider with SMTP works, such as Resend, Brevo, or Gmail with an app password |
| `MAIL_FROM` | Unset | Sender for those emails, for example `Kittok <no-reply@example.com>`. Without both, sign-up skips the email code |
| `HOST_PORT` | `3210` | Host-side loopback port in Compose |
| `HOST`, `PORT` | `127.0.0.1`, `3210` | Source server bind address and port; image binds internally to `0.0.0.0:3210` |
| `MEDIA_DIR` | `media/` | Media storage path; image uses its media volume |
| `CLIENT_DIR` | `client/` | Captured-client storage path; image uses its client volume |
| `MAX_VIDEO_MB` | `100` | Maximum uploaded source file size |
| `MAX_VIDEO_SECONDS` | `600` | Maximum video duration |
| `FFMPEG`, `FFPROBE` | `ffmpeg`, `ffprobe` | Video tool executables |
| `SOURCE_URL` | `/source` | URL where users can obtain the instance's current source |

After editing Compose environment settings, run `docker compose up -d` to recreate the app. Do not change the stored database password by merely editing `.env`; an existing PostgreSQL volume keeps its current database credentials.

## Running from source as a service

`deploy/kittok.service` runs a source install as a systemd user service: it starts the Postgres container first, restarts Kittok if it exits, and comes back after reboots when lingering is on (`loginctl enable-linger $USER`, once, as root). Adjust `WorkingDirectory` and the `Environment` line, then:

```bash
cp deploy/kittok.service ~/.config/systemd/user/ && systemctl --user enable --now kittok
```

`journalctl --user -u kittok -f` follows its log; `systemctl --user restart kittok` picks up new code.

## Registration and owner commands

Create accounts as the operator even while registration is closed:

```sh
docker compose exec app node scripts/create-user.mjs kitten
docker compose exec app node scripts/create-invite.mjs owner
```

Invites are single-use, expire after seven days, and are stored as hashes. Set `REGISTRATION_MODE=invite` to show invite-based registration at `/account?register=1`. A public registration request always creates a member; it cannot choose an administrator role. No default password or shared bootstrap key ships with Kittok.

For automation, `KITTOK_PASSWORD` can provide the create-user password through the process environment. Prefer the interactive prompt for manual setup. There is no password-reset email flow in this version.

Import an existing video by mounting or copying it into the app and running `scripts/import-video.mjs username /path/to/file.mp4 "Caption"`. The web uploader at `/account` handles normal uploads and transcodes them to H.264/AAC MP4. Posting is synchronous in this release, with two concurrent uploads per process. Uploaded files are public once imported; private video storage is not implemented.

## Backups and recovery

Back up the database and media together. Pause app writes while making a coherent snapshot:

```sh
mkdir -p backups
chmod 700 backups
docker compose stop app
docker compose exec -T db pg_dump -U kittok -d kittok -Fc > backups/database.dump
docker compose run --rm --no-deps --entrypoint tar app -cz -C /var/lib/kittok media client > backups/files.tar.gz
cp .env backups/instance.env
chmod 600 backups/*
docker compose start app
```

Keep backups off the server as well. The database dump contains accounts and session hashes; `instance.env` contains secrets. Restore into a fresh deployment with matching configuration: initialize an empty database, restore `database.dump` with `pg_restore`, extract `files.tar.gz` into the app's persistent storage as the app user, then start the app. Inspect restore errors before allowing writes. Do a recovery rehearsal before relying on a backup.

Named volumes are `postgres`, `media`, and `client`, scoped by the Compose project. `docker compose down` preserves them. The `-v` flag removes them and is not part of upgrades or routine restarts.

## Updates

1. Back up PostgreSQL, media, client cache, and `.env`.
2. Replace source files with the newer release, preserving `.env` and volumes.
3. Read its migration notes, then run `docker compose up -d --build`.
4. Verify `/health/ready`, login, feed playback, and uploads.

Migrations use a transaction and an advisory lock. Applied migration checksums must remain unchanged. Add a new migration for schema changes; never edit a migration that has already run. This release does not implement automatic downgrade migrations.

A client recapture is a separate operation. `docker compose exec app node scripts/capture.mjs` downloads the current public client and can require adapter updates. The server reads its pinned HTML at startup, so restart the app after a successful recapture. The client asset cache is not a guarantee that every screen will work offline.

## Multiple instances

Use a separate directory and `.env` for each instance, a unique public domain and host port, and a unique Compose project name:

```sh
docker compose -p kittenclub up -d --build
```

Compose project names isolate the volumes and service network. Set `HOST_PORT` to an available port and point that domain's reverse proxy at it. A user created on one instance does not automatically exist on another. There is no central Kittok account service or requirement to host on our domain.
